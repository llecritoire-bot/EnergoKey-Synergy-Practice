# ЕДИНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## 1. Среда

- Unity: **6.6 (6000.6.2f1)**.
- Шаблон: 2D.
- Язык: C#.
- Управление: экранные кнопки; для Editor добавить клавиатуру как вспомогательный способ.
- Ориентация: landscape.
- Git обязателен.

## 3. Базовая механика УП.ПМ.12

Создать работоспособный 2D-прототип:

- Player;
- стены/границы уровня;
- собираемые кристаллы;
- статические опасности;
- закрытый/открытый выход;
- экранные кнопки движения;
- HUD: число собранных кристаллов и жизни;
- победа;
- поражение;
- повторный запуск;
- особое правило: выход нельзя использовать до сбора всех кристаллов.

Код должен быть простым и читаемым. Не использовать сложный AI, pathfinding, стрельбу, физические головоломки, процедурную генерацию и сторонние платные пакеты.

## 4. Доработка ПП.ПМ.12

Довести прототип до завершённой игры:

### Уровни
- 3 проходимых уровня;
- рост сложности;
- различающиеся параметры;
- корректная победа и поражение;
- после третьего уровня — финальное сообщение/возврат в меню, но НЕТ уровня 4.

### Экраны
- Main Menu;
- Level Select;
- Gameplay;
- Pause;
- Victory;
- Defeat;
- Settings.

### Прогресс
Использовать понятный локальный механизм сохранения (например PlayerPrefs через отдельный SaveService):
- unlockedLevel;
- bestScore;
- masterVolume;
- tutorialSeen.

### Поведение
- следующая карта/уровень открывается только после победы;
- новая попытка сбрасывает только временное состояние уровня;
- потеря фокуса игры автоматически ставит игру на паузу;
- пауза реально останавливает игровую логику;
- настройки громкости сохраняются.

### Тестирование Т01–Т16
Провести и зафиксировать фактические проверки. Итоговая таблица должна содержать ID, ожидаемый результат, фактическое наблюдение, статус.

### Profiler
Сделать одно реальное обоснованное улучшение производительности и получить сравнение Profiler ДО/ПОСЛЕ в одинаковых условиях.

Рекомендуемая оптимизация: HUD сначала обновляется каждый кадр, затем переводится на событийное обновление только при изменении кристаллов/жизней/состояния. Сохранить отдельный commit/tag состояния ДО оптимизации и финальный commit ПОСЛЕ. Не подделывать Profiler.

## 5. Оформление УП.ПМ.13

На основе работающей игры сделать единый визуальный и звуковой стиль.

### Визуальный стиль
Сделать собственные простые 2D PNG-ресурсы, чтобы не было проблем с лицензиями:
- фон;
- игрок;
- кристалл;
- опасность;
- выход закрытый/открытый;
- UI-иконки.

Допустимо создать PNG программно (например Pillow) и зафиксировать в CREDITS: «создано автором работы».

Предлагаемый стиль:
- фон: тёмный графитовый;
- поверхность/панели: нейтрально-серые;
- игрок: голубой;
- кристалл/акцент: жёлтый;
- опасность: красная;
- успех/открытый выход: зелёный.

### Звук
Создать собственные короткие WAV-сигналы программно:
- collect;
- error/locked;
- damage;
- victory;
- defeat;
- button.

В CREDITS отметить как авторские/сгенерированные специально для учебного проекта.

### Prefabs
Сохранить как prefabs минимум:
- Player;
- Collectible;
- Hazard;
- UI Button.

### UI / HUD
Использовать Canvas Scaler, понятные anchors и масштабирование. HUD должен показывать:
- crystals: X/Y;
- lives: N;
- score.

Сделать визуальную и звуковую обратную связь для:
- правильного действия;
- неправильного действия (попытка войти в закрытый выход);
- повреждения;
- победы;
- поражения.

## 6. Подготовка к выпуску ПП.ПМ.13

### Адаптация экранов
Проверить как минимум:
- 1280×720 (16:9);
- 1440×720 (18:9);
- 1024×768 (4:3).

Все семь экранов должны быть читаемыми и кликабельными во всех форматах.

Реализовать Safe Area helper/adapter. В Editor должна быть возможность имитировать safe area, если реальное устройство недоступно.

### Обучение
Три карточки:
1. Управление — движение экранными кнопками.
2. Особое правило — сначала собрать все кристаллы, затем идти к выходу.
3. Победа/ошибка — опасности отнимают жизнь; при 0 жизней поражение.

Требования:
- при первом запуске обучение показывается автоматически;
- можно пропустить;
- после прохождения/пропуска автопоказ больше не появляется;
- кнопка «Как играть» снова открывает обучение с карточки 1;
- просмотр обучения не должен сбрасывать рекорды/прогресс.

### Панели
- Pause должна появляться плавно;
- во время появления игры остаётся на паузе (`Time.timeScale = 0`);
- повторные клики до завершения появления блокируются;
- скрытые панели не перехватывают нажатия (`CanvasGroup.blocksRaycasts = false` или эквивалент).

### Экран «Об игре»
Показать:
- «Энергоключ»;
- версию, например `1.0.0`;
- авторство: оставить нейтральный placeholder без ФИО либо «Автор: студент»;
- сведения о ресурсах: «Графика и звук созданы для учебного проекта».

Версия должна совпадать:
- на экране «Об игре»;
- Player Settings;
- README.

### Release
Создать:
- `Release/icon_512.png` — 512×512;
- `Release/promo_1280x720.png` — 1280×720;
- `Release/Screenshots/` — не менее 6 реальных игровых кадров;
- `Release/Docs/DESCRIPTION.md` — краткое описание до 80 знаков + полное 600–1200 знаков;
- `Release/Docs/PLAYER_GUIDE.md`;
- `Release/Docs/CREDITS.md`;
- `Release/Docs/CHANGELOG.md`;
- `README.md`;
- `Release/product_page_mockup.png` или HTML/PNG-макет;
- `Release/storyboard.md` с 6–8 кадрами демонстрации 60–90 сек., если видео автоматически создать невозможно.

## 7. Пользовательская проверка

Требование колледжа допускает самостоятельную проверку при отсутствии внешнего участника, но это нужно честно указать. Если Codex не может привлечь нового пользователя, он НЕ должен выдумывать человека.

Создать `EVIDENCE/USER_TEST.md`:
- формат проверки;
- дата;
- версия;
- устройство/Editor;
- сценарий;
- наблюдаемая проблема;
- исправление;
- повторная проверка.

Если внешнего пользователя не было: написать «самостоятельная проверка; требуется внешняя проверка новым пользователем». Никаких вымышленных ФИО.

## 8. Git

История должна позволять подтвердить этапы практик. Создать логичные коммиты/теги, например:

- `up-pm12-prototype`
- `pp-pm12-three-levels`
- `pm13-before-visual-style`
- `up-pm13-styled`
- `profiler-before`
- `pp-pm13-release`

Итоговый `README.md` должен содержать:
- Unity version;
- как открыть проект;
- какую сцену запускать;
- управление;
- структуру уровней;
- сохранения;
- известные ограничения;
- фактический commit hash финальной проверенной версии.

## 9. Никаких фиктивных доказательств

Нельзя:
- генерировать фальшивые скриншоты Unity Editor;
- выдумывать Profiler-цифры;
- заявлять тест «пройден», если он не запускался;
- выдумывать внешнего тестировщика;
- выдумывать Git URL, если репозиторий не опубликован.

Если технически невозможно запустить Unity/Profiler/GUI — создать проект и полный `MISSING_EVIDENCE.md` со списком того, что осталось получить вручную.
